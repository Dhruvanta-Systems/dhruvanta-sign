# How Digital Signatures Work in DocuSeal

> A complete explanation of how documents are signed, what makes them tamper-proof, and how security is enforced at every step.

---

## The Big Picture (Simple Version)

```
1. Signer draws/types their signature in the browser
2. DocuSeal stamps that signature image onto the PDF at the right position
3. DocuSeal then DIGITALLY SIGNS the entire PDF with a cryptographic certificate
4. Anyone can verify: "This PDF hasn't been changed since it was signed"

The drawn signature = what the human sees (visual)
The digital signature = what computers verify (cryptographic proof)
They are TWO DIFFERENT THINGS working together.
```

---

## Step-by-Step: What Happens When Someone Signs

### Step 1: Signer Draws Their Signature

The signer opens the form at `/s/:slug` and draws (or types) their signature in the browser.

- **Draw:** Canvas element captures pen strokes → saved as PNG image
- **Type:** Text rendered in a handwriting font (DancingScript) → saved as PNG image
- **Upload:** Signer uploads an image file

The signature image is uploaded to the server as an ActiveStorage attachment on the Submitter record.

### Step 2: Signer Submits the Form

When the signer clicks "Submit":

```ruby
# lib/submitters/submit_values.rb
submitter.completed_at = Time.current
submitter.ip = request.remote_ip        # IP address recorded
submitter.ua = request.user_agent       # Browser recorded
submitter.timezone = request.params[:timezone]
```

All field values (text, dates, checkboxes, signature image references) are stored in `submitter.values` as a JSON hash.

### Step 3: PDF Generation (The Critical Part)

`ProcessSubmitterCompletionJob` runs and calls `Submissions::GenerateResultAttachments`:

```
Original template PDF
        │
        ▼
For each field, STAMP the value onto the PDF:
  ├── Text fields → rendered as PDF text at the field's coordinates
  ├── Signature fields → signature PNG image placed at field coordinates
  ├── Date fields → formatted date text
  ├── Checkbox fields → check mark image
  ├── File fields → attached as PDF annotations
  └── etc.
        │
        ▼
Result: A filled PDF with all values visually embedded
        │
        ▼
DIGITAL SIGNATURE applied (see next section)
        │
        ▼
Stored as submitter.documents attachment
```

### Step 4: Digital Signature (Cryptographic)

This is where the real security happens. DocuSeal uses **X.509 PKI (Public Key Infrastructure)** — the same standard used by HTTPS, email encryption, and government digital signatures worldwide.

```ruby
# lib/submissions/generate_result_attachments.rb (line 737)
pdf.sign(io, 
  certificate: pkcs.certificate,      # X.509 certificate
  key: pkcs.key,                       # RSA private key
  certificate_chain: pkcs.ca_certs,    # Root CA + Sub-CA chain
  reason: sign_reason                  # "Signed by: john@example.com"
)
```

**What `pdf.sign` does internally (HexaPDF library):**

```
1. Compute SHA-256 hash of the ENTIRE PDF content
2. Encrypt that hash with the RSA private key → this is the "signature"
3. Embed the signature + certificate into the PDF's signature dictionary
4. Set the PDF's ByteRange (which bytes are covered by the signature)

Result: The PDF now contains:
  - The visible content (text, images, signatures)
  - A cryptographic signature proving the content hasn't changed
  - The certificate identifying who signed it
  - The certificate chain (Root CA → Sub-CA → signing cert)
```

### Step 5: Optional Timestamp (RFC 3161)

If a timestamp server is configured (`TIMESERVER_URL`):

```ruby
# lib/submissions/timestamp_handler.rb
# 1. Hash the PDF content
# 2. Send hash to a trusted timestamp authority (TSA)
# 3. TSA returns a signed timestamp token
# 4. Embed the timestamp in the PDF

# This proves WHEN the document was signed, not just BY WHOM
```

## The Certificate Chain

DocuSeal generates a 3-level certificate hierarchy:

```
┌─────────────────────────────────┐
│  Root CA                         │  Self-signed, 100-year validity
│  "DocuSeal Root CA"              │  Signs the Sub-CA
│  RSA 2048-bit, SHA-256           │
└──────────────┬──────────────────┘
               │ signs
               ▼
┌─────────────────────────────────┐
│  Sub-CA (Intermediate)           │  Signed by Root CA
│  "DocuSeal Sub-CA"               │  Signs the end-entity cert
│  RSA 2048-bit, SHA-256           │
└──────────────┬──────────────────┘
               │ signs
               ▼
┌─────────────────────────────────┐
│  End-Entity Certificate          │  Signed by Sub-CA
│  "DocuSeal"                      │  This is what signs PDFs
│  RSA 2048-bit, SHA-256           │
│  Key Usage: Digital Signature    │
└─────────────────────────────────┘
```

**Generated by:** `lib/generate_certificate.rb` on first setup.
**Stored in:** `EncryptedConfig` (encrypted at rest in the database).

### Self-Signed vs Trusted (AATL)

| | Self-Signed (default) | AATL Trusted (Pro) |
|---|---|---|
| Generated by | DocuSeal itself | A Certificate Authority (GlobalSign, DigiCert) |
| Adobe Reader shows | ⚠️ "Signature validity is UNKNOWN" | ✅ "Signature is VALID" |
| Legally valid in India? | Yes (IT Act 2000, Sec 5) | Yes, with stronger presumption |
| Tamper-proof? | Yes — identical cryptography | Yes — identical cryptography |
| Cost | Free | $200-2000/year for the certificate |

**Important:** Both self-signed and AATL use the EXACT SAME cryptographic process. The only difference is whether Adobe Reader's pre-installed trust list recognizes the Root CA. The math is identical.

## How Tamper Detection Works

### What happens if someone modifies the signed PDF

```
Original signed PDF:
  Content hash: a1b2c3d4e5f6...
  Signature: encrypted(a1b2c3d4e5f6...) with private key

Someone changes a single character:
  New content hash: x9y8z7w6v5u4...  (completely different!)
  Existing signature: encrypted(a1b2c3d4e5f6...)  (still the old hash)

Verification:
  Decrypt signature → a1b2c3d4e5f6...
  Compute current hash → x9y8z7w6v5u4...
  a1b2c3d4e5f6 ≠ x9y8z7w6v5u4
  → ❌ SIGNATURE INVALID — document has been tampered with
```

This is mathematically impossible to forge without the private key (RSA 2048-bit = 2^2048 possible keys to guess).

### SHA-256 Document Checksum

In addition to the PDF digital signature, DocuSeal stores a SHA-256 hash of every completed document:

```ruby
# app/models/completed_document.rb
# sha256 column stores the hash of the signed PDF file
CompletedDocument.create!(sha256: attachment.metadata['sha256'], submitter_id: submitter.id)
```

This provides a second layer of verification: even if someone replaces the entire PDF file, the stored hash won't match.

## Security at Every Layer

### During Signing (Browser → Server)

| Protection | How |
|---|---|
| HTTPS encryption | Caddy auto-SSL (TLS 1.2+). All data encrypted in transit. |
| CSRF protection | Rails CSRF tokens on every form submission |
| Unguessable URLs | 14-char Base58 slug = ~83 bits of entropy. Can't guess signing links. |
| IP + User-Agent recording | Stored on submitter record at completion time |
| Geolocation capture | GPS coordinates stored in metadata (if browser permits) |
| Session isolation | Each signer has their own slug. No shared sessions. |

### During PDF Generation (Server)

| Protection | How |
|---|---|
| Private key security | RSA private key stored in EncryptedConfig (Rails encrypted attributes) |
| Certificate chain | 3-level hierarchy (Root → Sub-CA → End-Entity) |
| Hash algorithm | SHA-256 (no known collisions, quantum-resistant for decades) |
| Timestamp | RFC 3161 trusted timestamp (optional, proves WHEN signed) |
| Atomic operation | PDF signed in a single transaction. No partial signatures. |

### After Signing (Storage + Verification)

| Protection | How |
|---|---|
| SHA-256 checksum | Stored in CompletedDocument table. Independent of PDF signature. |
| Audit trail PDF | Separate document recording: who, when, IP, browser, all events |
| Immutable events | SubmissionEvent records are append-only (never updated/deleted) |
| File integrity | ActiveStorage checksums on every blob |
| Blockchain notarization | Optional: hash written to Polygon blockchain (immutable public ledger) |

### Verification (Anyone Can Check)

```
Method 1: Open PDF in Adobe Reader
  → Shows signature panel with certificate details
  → Shows "Document has not been modified since signing"

Method 2: Use DocuSeal's verify endpoint
  POST /api/tools/verify (upload the PDF)
  → Returns: valid/invalid + signer details + timestamp

Method 3: Check SHA-256 hash
  sha256sum signed-document.pdf
  → Compare with CompletedDocument.sha256 in database

Method 4: Blockchain verification (if notarized)
  → Check transaction on Polygon explorer
  → Document hash in transaction data matches PDF hash
```

## Legal Validity (India)

| Law | What it says | How DocuSeal complies |
|---|---|---|
| IT Act 2000, Section 5 | Electronic signatures have legal validity | ✅ X.509 digital signature on PDF |
| IT Act 2000, Section 3A | Electronic signature = any electronic method that authenticates the signer | ✅ Drawn/typed signature + digital certificate + audit trail |
| Indian Evidence Act, Section 65B | Electronic records are admissible as evidence | ✅ Audit trail with IP, timestamp, browser, certificate |
| Indian Contract Act | Contracts require "free consent" | ✅ Signer actively draws signature and clicks submit |
| DPDP Act 2023 | Consent must be "free, specific, informed" | ✅ Document shown before signing, consent is per-field |

**What makes it legally strong:**
1. The signer actively drew/typed their signature (intent)
2. The digital certificate proves the document hasn't changed (integrity)
3. The audit trail records who, when, where, how (non-repudiation)
4. The timestamp proves when it happened (temporal proof)
5. The IP + browser prove the device used (attribution)
